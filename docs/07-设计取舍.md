# 设计取舍

这份文档解释「为什么这样做」，以及「为什么不那样做」。读它能避免很多“想当然”的改造。

## 1. 为什么用 JSON，不用数据库

- 数据量小：几十条判断、几千条对话，SQLite 甚至没必要。
- 可读可改：出问题时你能直接打开看，不用写 SQL。
- 可 diff：放进 Git 就能看每次变化。

代价是并发写没有事务保护。所以约定：**同一时间只让一个插件写 `store.json`**（复盘插件），其他插件只读。

## 2. 为什么不微调模型

- 成本高：每次性格变化都要重训。
- 不可控：微调会把「她」和「训练数据」混在一起，说不清哪来的。
- 不可回滚：改了权重就回不去了。

外置记忆可以随时改、随时删、随时回滚，这比“真的记住”更适合需要可控性的场景。

## 3. 为什么判断要人审

自动写入会让错误固化：模型误判一次，之后每次注入都在强化它。

所以流程是：**模型只产出提案，人回「同意」才写**。代价是每周花五分钟；收益是错误不会悄悄累积。

## 4. 为什么用概率，不用固定触发

固定触发会变成条件反射：一说“累”就念同一段。概率 + 冷却让同一场景下的反应有变化，但又不会完全随机。

概率不是越高越好：太高等于常驻，太低等于没有。默认值是按“几天遇到一次”调的。

## 5. 为什么 whim 只做「由头」，不直接发消息

直接发消息会变成打扰，而且平台限制多。做成“她此刻想起一件事，可以顺口提”，主动权还在对话里。

如果你想要真正的主动分享，用 `daily_ritual` 那类定时插件，别让 whim 承担。

## 6. 为什么不用图数据库

Graphiti 那套时间知识图谱很好，但需要 Neo4j/FalkorDB，运维成本远大于收益。
本项目的数据量用 JSON 邻接表（`insights` 数组 + 判断引用）足够表达“哪条洞察支撑哪条判断”。

等你真的有几千条实体和关系，再考虑图数据库。

## 7. 为什么不做多角色

多角色需要：角色隔离的记忆、发言调度、关系网。这是另一个量级的产品。
当前设计假设「一个主人 + 一个角色」，`scope` 只区分用途（陪聊/编程），不区分角色。

## 8. 隐私

- 所有数据在本地，没有云同步。
- 但注入内容会发给模型提供方，这一点无法避免。
- 群里不注入判断卡（`scope: private`），避免个人信息外泄。
- `raw/` 是明文聊天记录，注意电脑本身的访问权限。

## 9. 成本

| 项 | 量级 |
|---|---|
| 每轮注入 | 核心人格 2k 字 + 判断卡 0.5k + 世界书 0.3k + 阶段/状态 0.2k ≈ 3k 字 |
| 复盘 | 每周一次，一次几千 token |
| 存储 | 纯文本，一年也就几 MB |

真正贵的是模型调用本身，不是这套记忆。

## 10. 什么时候该换方案

- 需要多用户、多角色 → 上数据库 + 服务化
- 需要跨设备同步 → 记忆目录放对象存储，加锁
- 需要“自动学习”而不是“人工审” → 接受错误固化，或加更强的冲突检测
- 需要视觉小说式 UI → 换 SillyTavern / 自研前端

这套的定位是：**单机、单角色、可读可改、低依赖**。
